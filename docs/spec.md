# ТЗ: классификатор обращений в поддержку

Oct 21, 2026 · @beornir

## Цель задания

За неделю собрать на Python небольшой сервис, который классифицирует обращения в поддержку с помощью LLM, и измерить качество его работы на собственном наборе примеров.

После задания студент умеет:

- поднять Python-проект с uv и FastAPI;
- описать вход и выход сервиса через Pydantic-схемы;
- получать от LLM ответ строго по JSON-схеме (structured output);
- собрать eval-набор и посчитать метрики качества;
- улучшать промпт итерациями, опираясь на цифры, а не на ощущения.

Главный результат недели — не «работающий бот», а README с цифрой качества и объяснением, как она менялась.

## Функциональные требования

Сервис принимает текст обращения клиента и возвращает его категорию, срочность и краткое резюме.

| Эндпоинт | Метод | Что делает |
| --- | --- | --- |
| `/classify` | POST | Классифицирует одно обращение |
| `/health` | GET | Возвращает `{"status": "ok"}` для проверки, что сервис жив |

Пример запроса и ответа:

```json
// POST /classify
{"text": "Не приходит код из SMS, третий день не могу войти в приложение"}

// 200 OK
{
  "category": "auth",
  "urgency": "high",
  "summary": "Клиент не получает SMS-код и не может войти"
}
```

Категории — фиксированный список, других значений сервис возвращать не должен:

| category | Что сюда относится |
| --- | --- |
| `auth` | Вход, регистрация, пароли, SMS-коды, блокировка аккаунта |
| `payment` | Оплата, списания, возвраты, тарифы, чеки |
| `delivery` | Доставка, сроки, статус заказа, курьер |
| `technical` | Ошибки и сбои приложения или сайта, не связанные со входом |
| `other` | Всё остальное: отзывы, предложения, вопросы не по теме |

Срочность:

| urgency | Когда ставится |
| --- | --- |
| `high` | Клиент не может пользоваться сервисом или теряет деньги прямо сейчас |
| `medium` | Проблема мешает, но есть обходной путь или она не критична по времени |
| `low` | Вопрос, пожелание, отзыв — ничего не сломано |

Поле `summary` — одно предложение на русском, не длиннее 150 символов.

Обработка ошибок:

- пустой текст или текст длиннее 4000 символов → `422` с понятным сообщением;
- модель недоступна или вернула невалидный ответ → `502`, ошибка пишется в лог;
- сервис не должен падать ни на одном входе из eval-набора.

## Технические требования

Стек фиксированный: Python 3.11+, uv, FastAPI, Pydantic v2 и SDK любого LLM-провайдера с поддержкой structured output.

1. **Окружение.** Проект создаётся через `uv init`, все зависимости — в `pyproject.toml`, лок-файл `uv.lock` в репозитории. Запуск: `uv run uvicorn app.main:app`.
2. **Схемы.** Запрос и ответ описаны Pydantic-моделями. `category` и `urgency` — `Literal` или `Enum`, а не произвольные строки.
3. **Structured output.** Ответ модели запрашивается сразу по JSON-схеме из Pydantic-модели через механизм провайдера (response format, tool calling). Парсить JSON регулярками из свободного текста нельзя.
4. **Промпт отдельно от кода.** Системный промпт лежит в `prompts/classify.md` и читается при старте. Любое изменение промпта — отдельный коммит.
5. **Секреты.** API-ключ только в `.env`, файл в `.gitignore`. В репозитории — `.env.example` без значений.
6. **Параметры модели.** Название модели и temperature задаются в конфиге или `.env`, не захардкожены. Для классификации рекомендуемая temperature — 0.
7. **Типизация.** Все функции с type hints. Код проходит `ruff check` без ошибок.

Выбор провайдера и модели — на усмотрение студента. Главное условие: на весь eval-набор должна хватать бесплатной квоты или нескольких долларов.

## Eval-набор и оценка качества

Это главная часть задания: без eval-набора работа не принимается, даже если сервис работает идеально.

**Набор.** Файл `evals/dataset.jsonl`, минимум 30 примеров, каждый — отдельная строка:

```json
{"id": 1, "text": "Деньги списались дважды за один заказ", "category": "payment", "urgency": "high"}
{"id": 2, "text": "Подскажите, можно ли изменить адрес доставки?", "category": "delivery", "urgency": "low"}
```

Требования к примерам:

- каждая категория представлена минимум 4 примерами;
- не меньше 8 «сложных» примеров, помеченных полем `"hard": true`: обращения на стыке двух категорий, с опечатками, на смеси русского и казахского или английского, очень короткие («не работает») или очень длинные, с сарказмом;
- примеры пишутся вручную, своими словами, — генерировать набор той же моделью, которую оцениваете, нельзя;
- разметка делается до запуска модели, а не подгоняется под её ответы.

**Скрипт.** `evals/run_eval.py` прогоняет весь набор через сервис или напрямую через функцию классификации и выводит:

- accuracy по `category` и отдельно по `urgency`;
- accuracy отдельно на сложных примерах;
- матрицу ошибок по категориям: что с чем модель путает;
- список всех ошибок: id, текст, ожидание, ответ модели.

Результат каждого прогона сохраняется в `evals/results/<дата-время>.json`, чтобы прогоны можно было сравнивать.

**Итерации.** Студент делает минимум 3 версии промпта и прогоняет каждую на одном и том же наборе. Менять набор между прогонами, чтобы цифра выросла, нельзя: новые примеры добавляются только вместе с повторным прогоном всех версий.

## Бонусные задания

Необязательны и дают дополнительные баллы, но только при выполненной основной части.

| Задание | Что сделать | Баллы |
| --- | --- | --- |
| Docker | Dockerfile и запуск сервиса одной командой `docker compose up` | +5 |
| Стриминг | Эндпоинт `POST /reply`, который генерирует черновик ответа клиенту и отдаёт его потоком через SSE | +5 |
| Сравнение моделей | Прогнать eval-набор на двух моделях или двух temperature, сравнить качество, время ответа и стоимость | +5 |
| Пакетная обработка | Эндпоинт `POST /classify/batch` на список обращений с параллельными запросами через asyncio | +5 |

Максимум за бонусы — 15 баллов, даже если сделано больше.

## Критерии оценки

Основная часть — 100 баллов, зачёт от 60. Сама итоговая accuracy баллов не даёт: оценивается, насколько честно она измерена и как студент с ней работал.

| Критерий | Что проверяется | Баллы |
| --- | --- | --- |
| Eval-набор | Объём, покрытие всех категорий, качество сложных примеров, разметка до прогона | 25 |
| Работающий сервис | Эндпоинты по спецификации, корректные коды ошибок, не падает на наборе | 20 |
| Код и стек | uv, Pydantic-схемы, structured output, промпт в файле, конфиг, ruff | 15 |
| Скрипт оценки | Все метрики, матрица ошибок, сохранение результатов прогонов | 15 |
| Итерации промпта | Минимум 3 версии, отдельные коммиты, журнал с цифрами | 15 |
| README и выводы | Запуск с нуля, разбор ошибок, честный вывод об ограничениях | 10 |

Работа не принимается без доработки, если:

- API-ключ попал в репозиторий, даже в истории коммитов;
- нет eval-набора или скрипта оценки;
- сервис не запускается по инструкции из README.

## Сроки и частые вопросы

Срок — 7 дней с момента выдачи задания. Дата сдачи: [указать]. Ссылка на репозиторий отправляется [куда — указать].

Рекомендуемый план недели:

1. Дни 1–2 — поднять проект, сделать `/classify` со structured output.
2. День 3 — написать и разметить eval-набор.
3. Дни 4–5 — скрипт оценки и минимум три итерации промпта.
4. День 6 — README, разбор ошибок, бонусы по желанию.
5. День 7 — запас и проверка запуска с нуля.

**Можно ли пользоваться AI-ассистентами для кода?** Да. Но eval-набор пишется вручную, и на защите нужно уметь объяснить любую строку своего кода.

**Нужен ли интерфейс?** Нет. Интерфейс не оценивается; проверяются API, eval-набор и README. Для ручной проверки хватит Swagger, который FastAPI генерирует сам по адресу `/docs`.

**Можно ли писать не на Python?** Нет. Python — часть цели задания.

**Что если accuracy сразу 100%?** Значит, набор слишком простой. Добавьте сложных примеров, пока модель не начнёт ошибаться, — именно на ошибках видно, как работает промпт.

**Какую модель выбрать?** Любую с поддержкой structured output. Небольшой модели обычно хватает: для этой задачи важнее промпт и набор, чем размер модели.
